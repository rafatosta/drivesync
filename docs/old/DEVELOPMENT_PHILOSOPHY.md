# Development Philosophy

## Engineering first, AI-assisted implementation

DriveSync has two goals: to build a useful, GNOME-native Google Drive client for Linux, and to explore a software development workflow in which a human maintainer leads engineering while AI agents implement code.

The central idea is straightforward: **software engineering is more than writing source code**. Understanding a problem, defining requirements, evaluating trade-offs, designing architecture, reviewing results, testing, and maintaining the product are distinct activities. Writing code is one of them.

This is not a claim that AI-generated code is inherently better than human-written code, or that AI removes the need for technical expertise. It is an attempt to apply established engineering practices while delegating implementation to AI agents.

## Start with the problem, not the language

The development process starts by identifying the problem and the expected behavior of the product. Technology follows the requirements, rather than the maintainer's familiarity with a programming language.

For DriveSync, Python, C++, and Rust were considered. Rust was selected following a discussion of the project's needs and trade-offs, not because all other languages were incapable of implementing the solution. The project uses GTK4 and Libadwaita to integrate with GNOME.

Architectural choices likewise follow product constraints: clear separation between the user interface and synchronization engine, modular responsibilities, per-account state, and attention to recoverability and data safety.

These are design intentions and decisions, **not evidence that every planned feature has been implemented or verified**.

## A team-like delegation model

The workflow is inspired by how a software engineering team divides responsibilities:

1. **Problem and requirements:** The maintainer identifies needs, scope, constraints, and acceptance criteria, with AI agents available as discussion partners.
2. **Analysis and design:** Alternatives are explored, trade-offs are discussed, and architectural decisions are documented. Suggestions can originate from either the maintainer or an agent; the maintainer chooses what to adopt.
3. **Implementation:** AI coding agents translate scoped specifications into Rust modules, interfaces, refactors, and supporting code. The maintainer does not currently write the Rust implementation manually.
4. **Review and verification:** Deliveries are reviewed against requirements through code inspection where appropriate, builds, tests, and hands-on checks. Defects lead to further investigation and changes.
5. **Maintenance and evolution:** Bugs and new requirements are triaged, specified, delegated, verified, and documented through the same cycle.

The analogy is about **dividing work**, not treating AI agents as accountable human employees. Agents can propose or implement solutions, but they cannot assume professional responsibility for the resulting software.

## Who decides what?

The maintainer is responsible for product direction, prioritization, accepting trade-offs, coordinating work, and deciding whether an implementation is ready.

AI agents support research, discussion, documentation, code generation, refactoring, and diagnosis. Architectural recommendations can emerge from these discussions; the project does not claim that every technical idea originated with the maintainer.

The source code is generated by AI agents, but this does not make their outputs automatically trustworthy. Generated explanations may be incomplete or wrong, and code can fail in ways that are not immediately visible.

## How quality is assessed

**Code origin is not a quality metric by itself.** Human and AI implementations can both contain errors. What matters is whether the system meets its requirements and is demonstrably safe, maintainable, and correct for its intended purpose.

Depending on a component's risk, verification should include:

- Defined behavior and acceptance criteria.
- Consistency with module responsibilities and interfaces.
- Build checks and automated tests where available.
- Integration and manual functional testing.
- Inspection of error handling, security-sensitive code, and data persistence.
- Additional safeguards for actions affecting credentials or user files.

AI reviewing AI is useful feedback, but it is **not a substitute for independent evidence** such as reproducible tests and human acceptance checks. A successful build or a working interface alone does not prove that the synchronization engine is correct.

These are process goals: coverage and verification must be reported honestly as the implementation matures.

## Scope of the experiment

DriveSync is intended to evolve beyond a prototype into maintainable software. The approach will therefore be evaluated not only by how quickly an MVP can be assembled, but also by whether the application can be tested, debugged, changed, and supported over time.

This is **not** a claim that the approach has already been proven successful. Limitations, design mistakes, bugs, and unverified components remain part of the development process and should be documented.

The project currently supports account connection, folder browsing, and configuration flows in an early technical preview. **File downloads and synchronization do not work yet.** See the [README](../README.md) for the current status and supported behavior.

## AI-assisted development and “vibe coding”

Generating code with AI does not, by itself, describe how a software project is engineered. The term *vibe coding* is often used for workflows that prioritize prompting and observing a result without closely examining the underlying implementation.

DriveSync instead **aims for requirements-driven, reviewed, and testable development**. Whether it succeeds depends on the actual reviews, tests, architecture, and behavior—not on the label used or the author of the code.

This document is intended to make the development method transparent, not to dismiss other workflows or guarantee software quality.

---

**Guiding principle:** Implementation can be delegated; responsibility for engineering decisions, verification, and the resulting product remains human.
