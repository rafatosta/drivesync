# Inventory observation ordering

Inventory decides whether an observation may update persisted state using markers stored per item and side (local or remote). The durable order is scoped to one synchronization and is allocated by the Detector's SQLite causal clock. Scanner reserves from that same clock before collecting a local entry; Local Detector reserves before collecting a notification result; Operator verification reserves separately for each side immediately before collecting that side's metadata. Inventory persistence never creates evidence of physical freshness. A versionless remote response without a comparable collection position remains uncertain; inserting it into the durable event queue does not make it newer.

For local observations, Inventory compares only the durable causal positions. A greater position may update the local side; a smaller position is obsolete. An absent position, or a side without a comparable saved position, is incomparable. Generation labels and system timestamps do not establish order.

For remote observations, Inventory first compares decimal provider versions when both sides carry one. A greater version may update state and a smaller version is obsolete. Successful Operator verification stores the verified provider version together with that side's pre-collection causal position, so a queued version 11 cannot replace a version 12 confirmed by the Operator even if the queued event carries a larger unrelated position. When versions are missing or not comparable, Inventory uses a comparable durable causal position; otherwise it records uncertainty. Provider versions are stored as decimal text and compared numerically.

An obsolete observation receives a durable `Obsolete` receipt. An incomparable observation receives a durable `Incomparable` receipt and a durable Inventory revalidation record keyed by item and side. It leaves the item and optimistic revision unchanged. The responsible Detector receives a localized request, and the Flow replays persisted revalidation records after restart. A comparable observation removes the record in the same transaction that applies its state and receipt. The event lease is acknowledged only after the request and any required analysis succeed. If the process fails before acknowledgement, the durable Detector event is redelivered; its Inventory receipt makes the action idempotent while allowing the interrupted request or analysis to run again. Applied observations preserve the existing optimistic revision check and write the new side marker in the same Inventory transaction as the state change and receipt.

The causal clock is incremented in an immediate SQLite transaction and survives application restarts. Pending queue records retain their producer-assigned position across delivery retries and restart. Scanner and Local Detector can reserve concurrently: SQLite serializes reservations, providing a shared frontier without making either module depend on the other. Remote events without provider versions are not assigned a position at queue insertion because concurrent provider queries and earlier pending results make insertion order insufficient proof. Revalidation work is persisted in Inventory schema 11; older Inventory schemas are rejected, with no migration in this development phase. An event without comparable evidence is never ordered by arrival time or `observed_at`.

The order is evidence about when each producer began an observation or confirmed a verified result. It is not a conflict-resolution or operation-execution policy. Revalidation is localized through the responsible Detector and does not restart Scanner in continuous operation.
